# 拣货空跑分析：先拦截“陈旧库存或极低库存”任务

## 我的判断

这批数据中最值得优先解决的不是路线长短，而是**派单依据的库存信息已经过时**，其次是**账面库存只剩极少数量**。

- 原文件 1,303 行中有 62 行完全重复；去重后 1,241 条记录，其中 50 条作业中断、结果未知，主分析使用其余 1,191 条。
- 1,191 条有效记录有 150 次到位缺货，空跑率 **12.59%**，按每次 120 分钟计，共 **18,000 分钟（300 小时）**损失。
- 库存同步延迟不超过 15 分钟时，空跑率仅 **4.18%（37/885）**；延迟超过 15 分钟后升至 **36.93%（113/306）**，是前者的 **8.8 倍**。
- 路线步数不是首要根因：25 步以内空跑率 7.69%，56-70 步为 16.18%，但这一字段只影响一次空跑有多浪费，不解释库位为什么没货。

因此，我建议将“库存新鲜度”变成派单前置条件，而不是让拣货员到位后才发现账实不符。

> 数据限制：仓库和设备品类中文在发放的 CSV 中已经是 Unicode 替换字符，无法可靠恢复原名。本分析保留这些字段但不凭乱码命名重点对象。所有重复 `task_id` 行均为完全相同记录，因此按整行去重；空结果不当作成功或失败。

## 做了什么

采用按时间排序的 70%/30% 切分：只在较早的 833 条记录上，从可解释规则族中选择成本最低的阈值，再在较晚的 358 条完全未参与选阈值的数据上验证。

建议试点规则：

```text
若 库存同步延迟 >= 18 分钟 OR 账面库存 <= 3 件：
    暂缓派单，先花约 12 分钟核验库存；确认缺货则标缺并改派
否则：
    正常派单
```

这是一条派单前规则，不要求改变拣货员路线，也不需要黑盒模型。18 分钟和 3 件是训练段按题目给定成本（空跑 120 分钟，提前核验/标缺 12 分钟）选出的阈值。

## 怎么证明有用

在后 30% 时间留出集（358 条）中：

| 指标 | 结果 |
|---|---:|
| 实际空跑 | 58 次 |
| 规则触发核验 | 109 条（30.4%） |
| 提前覆盖空跑 | 50 次（召回率 86.2%） |
| 触发任务中的真实空跑率 | 45.9% |
| 原空跑损失 | 6,960 分钟 |
| 规则后估算损失 | 2,268 分钟 |
| 净节省 | **4,692 分钟（78.2 小时，67.4%）** |

估算公式为：

```text
原损失 = 空跑数 × 120
规则后损失 = 触发核验数 × 12 + 未覆盖空跑数 × 120
```

固定规则在留出集上进行 5,000 次 bootstrap，净节省分钟数的 95% 区间为 **[3,300, 6,132]**，区间仍为正。

这是基于历史标签的反事实估算，不是已经完成的线上因果实验。它假设一次核验能避免被覆盖的空跑；上线应做 1-2 周 A/B 或分仓阶梯试点，主指标为“每 100 单总损失分钟”，同时监控核验量、空跑率、发货时效和中断率。

## 复现

环境：Python 3.10+。

```bash
python -m pip install -r requirements.txt
python analysis.py
```

脚本会校验和读取仓根的 `pick_records.csv`，去重、构造库存同步延迟、按时间切分、选择规则并评估，生成：

- `outputs/metrics.json`：全部指标、阈值和数据质量信息
- `outputs/failure_rate_by_stock_age.csv`：同步延迟分桶空跑率
